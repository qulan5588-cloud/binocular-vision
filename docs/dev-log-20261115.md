## 带宽实测（验证"延长线是否限带宽"）
- 主机为 ThinkStation P3 Tower (30GUA51JCW)，全机无 USB2.0 口：前面板 2×USB-A 5Gbps + 2×USB-A 10Gbps + 1×USB-C 10Gbps，后面板 4×USB-A 5Gbps。单 Intel xHCI 3.20 控制器，2 个根集线器（SS 通道空闲）。
- RGB 实测：2048x1536@30fps 满帧零丢帧，码率 44.2 Mbps；1920x1080@30 为 28.9 Mbps / 3.45 MB/s。
  → 能稳定跑 44 Mbps 证明链路是 High Speed(480Mbps)，延长线未导致降速到 Full Speed。
- 带宽账：深度 Y16 640x480@30 = 17.6 MB/s + IR 17.6 MB/s + RGB 3.45 MB/s ≈ 38.6 MB/s，已达 USB2.0 HS 实用上限的 97%~110%。
  → 结论：延长线不是瓶颈；真正的瓶颈是 USB2.0 上行共享带宽。
  ⚠️ 更正：05E3:0608 **不是外置 HUB，而是相机内部的 HUB 芯片**（Genesys GL850G，位置 Port_#0005.Hub_#0001 即相机所插的根端口）。Astra Pro Plus 只有**一根 USB 线**，内部 HUB 分出 Port1=深度(060F)、Port2=彩色(050F)。
  → 因此"深度与彩色分插两个根端口"不可行，两路必然共用一条 480Mbps 上行。
  → 实际可用组合：深度(17.6) + RGB(3.45) ≈ 21 MB/s，约占 60% 带宽，可行；再加 IR(17.6) ≈ 38.6 MB/s 会超限，三路同开不可行。

## 彩色掉帧根因定位（17:30-18:05）—— 结论反转
排除法实测，逐层否定了此前所有假设：
1. 链路：相机在线，2 层 HUB（1A40 外置 + 05E3 相机内），与掉帧无因果关系
2. 光线：抓帧分析 mean=141/255、过曝 22.6% → 不是自动曝光压帧率
3. 带宽：ffmpeg `-c:v copy` 落盘，640x480 / 1280x720 / 1920x1080 **三个分辨率都是 150帧/5秒 = 30fps**
   → 相机与 USB 链路完全正常，1080p 也满帧
4. 真正的瓶颈：**OpenCV 5.0.0 的 MJPG 解码吞吐仅 ~6.6 MP/s**
   - 720p 7.1fps、1080p 3.2fps（数字与像素数严格成反比，证明是解码而非带宽）
   - grab() 瞬间返回但 retrieve() 极慢 → 瓶颈在解码不在取流
   - BUFFERSIZE、CONVERT_RGB、MSMF 后端都无改善（MSMF 直接报 -2147483638）
5. Windows subprocess 管道也有天花板：Python 纯读约 4.11MB/s，cat 可达 6.10MB/s
   → 1080p 需 5.6MB/s 喂不饱，720p 仅需 1.8MB/s 有余量

解决方案（已验证）：ffmpeg 管道 `-c:v copy -f mjpeg pipe:1` 取 MJPG 裸流，Python 完全不解码，
按 JPEG SOI/EOI 切帧，直接以 .jpg 落盘。省掉"解码+重新编码"两次开销。
- 实测 720p 双流：深度 30.1fps、彩色 30.0fps、同步差 均值 9.5ms/中位 6.0ms/P95 29ms
- 对比改造前：彩色 3.2fps、同步 57ms

代码改动：
- capture_pair.py 新增 `ColorSourceFFmpeg`（is_jpeg=True，latest() 返回 (jpg_bytes, ts)）、
  `find_ffmpeg()`、常量 `FFMPEG_DEVICE="USB Camera"`
  - 新参数 `--color-backend {auto,ffmpeg,dshow}`（默认 auto→ffmpeg）、`--device`
  - `save_pair()` 拆出 `write_color()`，jpeg 后端写 .jpg 原始字节，dshow 后端仍走 imwrite_u 存 png
  - 预览改为每 250ms 解码一次（4fps），避免拖累主循环
